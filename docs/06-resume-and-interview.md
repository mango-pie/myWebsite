# Knowledge AI 简历与面试材料

## 1. 简历项目名称

AI 智能知识库系统 Knowledge AI

## 2. 简历项目描述

基于 Spring Boot 3、Spring AI 和 Vue3 构建的企业级 AI 知识库问答平台，支持文档上传、文本解析、文本切块、Embedding 向量化存储、RAG 检索增强生成、多轮对话和 SSE 流式输出。

系统采用 Spring Security + JWT 实现前后端分离认证，Redis 缓存登录态和热点数据，MySQL 存储用户、知识库、文档、会话等业务数据，MinIO 存储原始文档文件，PostgreSQL + pgvector 实现向量存储与语义检索，前端基于 Vue3、TypeScript 和 Element Plus 实现响应式后台与聊天交互。

## 3. 简历技术亮点

- 使用 Spring Security + JWT 实现前后端分离认证授权，并结合 Redis 管理登录态，实现 Token 校验、主动失效和接口权限控制。
- 使用 MinIO 存储用户上传文档，MySQL 仅保存文件元数据，实现文件存储与业务数据解耦。
- 基于 Spring AI 实现 PDF 文档解析、文本切块、Embedding 向量化和 pgvector 向量入库。
- 使用 PostgreSQL + pgvector 实现语义相似度检索，支持按知识库范围召回 TopK 文档片段。
- 采用 RAG 架构将检索结果注入 Prompt，提升大模型回答的准确性和知识可控性。
- 使用 SSE 实现 AI 回复流式输出，前端实时渲染 Markdown 和代码块，提升用户交互体验。
- 设计 conversation 和 message 数据模型，支持多轮对话、历史记录和知识库上下文问答。
- 扩展支持多模型配置、Prompt 模板管理、Token 统计和 AI 参数动态调整。

## 5. 面试讲解主线

面试介绍项目时，建议按下面顺序讲：

1. 项目首先实现基础后台，包括用户注册、登录、JWT 鉴权、权限控制和用户管理。
2. 然后实现知识库和文档管理，用户可以创建知识库并上传 PDF、DOCX、TXT、Markdown 等文件。
3. 文件上传后保存到 MinIO，MySQL 只保存文件元数据，避免数据库直接存储大文件。
4. 文档进入 RAG 入库流程后，系统读取文档内容，将长文本切成多个 Chunk。
5. 每个 Chunk 调用 Embedding 模型生成向量，并保存到 PostgreSQL + pgvector。
6. 用户提问时，系统先把问题向量化，再从向量数据库中检索最相关的 TopK 文档片段。
7. 系统将检索结果和用户问题组装成 Prompt，调用大模型生成回答。
8. 最后通过 SSE 将回答流式返回前端，实现类似 ChatGPT 的实时输出效果。

## 6. 核心问题回答

### 为什么要做文本切块？

因为文档通常比较长，直接把整份 PDF 输入给大模型可能超过上下文长度限制。即使没有超过，也会导致 Token 成本高、噪声多、回答不聚焦。切块后可以只检索和用户问题最相关的片段，提高回答质量并降低成本。

### 为什么不能直接把 PDF 喂给大模型？

PDF 可能包含几十页甚至几百页内容，超过模型上下文窗口。同时完整文档中包含大量与当前问题无关的信息，直接输入会降低回答准确性。RAG 的做法是先把文档拆成 Chunk，再根据问题召回相关片段，让模型只基于有用上下文回答。

### 为什么需要 Embedding？

Embedding 可以把文本转换成语义向量。这样用户即使没有使用文档中的原始关键词，系统也能通过语义相似度找到相关内容。例如用户问“怎么重置账户密码”，文档里写的是“修改登录凭证”，向量检索仍然可能召回相关片段。

### 为什么使用向量数据库？

向量数据库可以高效存储和检索高维向量，支持相似度搜索。项目中使用 PostgreSQL + pgvector，可以在保存向量的同时结合知识库 ID、文档 ID、用户权限等业务字段进行过滤，非常适合中小型知识库系统。

### 为什么使用 SSE？

大模型生成回答通常需要一定时间，如果等待完整结果生成后再返回，用户体验会比较差。SSE 可以让后端边生成边推送，前端实时展示回复内容，交互体验更接近 ChatGPT。

### 为什么文件用 MinIO，不直接存 MySQL？

文档文件属于大对象数据，如果直接存入 MySQL，会增加数据库压力，也不利于文件下载、迁移和扩展。使用 MinIO 可以把文件存储和业务数据解耦，MySQL 只保存文件元数据和对象存储 Key，后续也方便迁移到云对象存储。

### JWT 为什么还要结合 Redis？

JWT 本身是无状态的，服务端签发后无法主动让它失效。如果用户退出登录、修改密码或账号被禁用，仅靠 JWT 很难立即拦截旧 Token。结合 Redis 保存登录态后，服务端可以通过删除 Redis 登录信息实现 Token 主动失效。

## 7. 面试项目介绍示例

可以这样介绍：

我做了一个 AI 智能知识库系统，主要解决企业私有文档的智能问答问题。用户可以创建知识库并上传 PDF、DOCX、TXT、Markdown 等文档，系统会把文件保存到 MinIO，MySQL 保存文档元数据。文档上传后会进入 RAG 入库流程，通过 Spring AI 读取文档内容，使用 TokenTextSplitter 进行文本切块，再调用 Embedding 模型生成向量，并保存到 PostgreSQL + pgvector。

用户提问时，系统会先将问题向量化，然后在当前知识库中检索 TopK 相关文档片段，把检索结果注入 Prompt，再调用大模型生成回答。为了提升交互体验，我使用 SSE 实现了流式输出，前端可以像 ChatGPT 一样实时展示 AI 回复。同时系统也支持多轮对话和历史消息保存。

基础后台方面，我使用 Spring Security + JWT 实现前后端分离认证，并结合 Redis 保存登录态，这样可以支持退出登录和修改密码后的 Token 主动失效。

## 8. 项目难点总结

### 难点一：RAG 链路较长

RAG 涉及文档读取、文本清洗、文本切块、Embedding、向量存储、向量检索、Prompt 组装和模型调用，任何一个环节处理不好都会影响最终问答效果。

解决方式：

- 将文档解析、切块、向量化、检索拆成独立服务
- 为文档增加解析状态
- 记录失败原因，支持重新解析
- 通过 Chunk 数量和检索结果排查链路问题

### 难点二：长文档处理

长文档直接输入大模型不可行，需要合理切块。

解决方式：

- 使用 TokenTextSplitter 控制 Chunk 大小
- 设置适当 Overlap 保留上下文连续性
- 保存 Chunk 顺序和来源文档
- 检索时限定 TopK，避免 Prompt 过长

### 难点三：流式输出

SSE 需要处理连接中断、异常返回和最终消息保存。

解决方式：

- 后端分片推送模型输出
- 前端逐步追加内容
- 完成后保存完整 AI 回复
- 异常时发送 error 事件并结束连接
